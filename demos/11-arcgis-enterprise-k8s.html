Esri system architecture (researched) 
Source: ArcGIS Enterprise on Kubernetes documentation — System architecture,
Understanding system deployments, Availability profiles, Manage service deployments.

Organization: Kubernetes cluster → namespace "arcgis" → four pod categories
(plus supporting system deployments Esri lists separately).

1. Framework — ingress + private ingress; Help; Services API; Apps; JavaScript API;
   Notebook automation; Service lifecycle manager; Web styles; usage metrics.

2. Administration — Administrator API (/admin); Enterprise Manager (/manager);
   Organization UX (/home); Portal sharing API (/sharing/rest).

3. GIS / system / utility — map, feature, geocode, GP, notebook, tile, image services;
   shared feature/map/tile/image resources; system PublishingTools & RasterAnalysisTools;
   utility geometry & printing. Shared vs dedicated scaling via Manager / Admin API.
   Optional: federate Windows/Linux server sites; register user-managed data stores.

4. System storage (StatefulSets + PVs, or cloud for object/relational) —
   Object store (uploads, tile/image caches, GP output);
   Relational store primary + standby (hosted features, config);
   Spatiotemporal & index store (logs, indexes, hosted features);
   Queue store; in-memory cache; item packages; Prometheus.
   Replicas / PV sizes set by availability profile (Development · Standard HA · Enhanced HA).
   System storage pods are not independently scaled at this release.

Pods distribute across worker nodes. Diagram is detailed but still an overview —
Esri’s published architecture diagram is also “not a complete inventory.”
